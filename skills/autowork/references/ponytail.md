# Ponytail inside Autowork

Apply the smallest complete change method to the selected task. Autowork keeps
task ownership, acceptance, the existing review lane and delivery authority.

## Resolve the method once

For a material choice about new logic, dependencies, abstraction or reuse, load
the active `ponytail:ponytail` skill from the current host/profile catalog, or its
verified SKILL.md path. Inspect the content: a retired compatibility shim is not
Ponytail. Respect an explicitly requested level; otherwise use full's method
within this task. Do not enable persistent modes, install plugins or change
profiles. Reuse instructions already read for the same task and version.

If missing or blocked, report that limitation and use the method below. Do not
claim plugin execution. Trivial edits use the method directly without a skill
load or ceremonial receipt. Missing optional guidance does not block execution;
missing required execution or review capability still does.

## Choose before adding code

Read the accepted outcome and connected callers, tests, fixtures, exports and
config. Take the first option that fully satisfies acceptance and repository
conventions: omit unrequested extras; reuse existing code; use standard library
or platform features; use an installed dependency; write minimal readable code.
A house component wins over a replacement platform widget. Fix the shared cause
when callers share the defect. Keep validation and error handling when moving code.
Complete all affected consumers and relevant regression coverage. Fewer lines
never justify dropping security, accessibility, data safety or accepted behavior.

Carry a material decision in the existing contract/receipt:
`Ponytail: source=<verified skill/revision or bundled fallback>; decision=<choice>;
reuse=<paths>; omitted=<unneeded extras or none>; check=<command/result or pending>.`
For example, reuse the repository's CSV export helper and its escaping tests;
omit a new serializer abstraction. Record actual checks after running them.
Reuse unchanged source-bound decisions; revisit only affected choices when inputs
or evidence change. No separate ledger or repeated repository audit.

## Review the same candidate

The existing reviewer resolves `ponytail:ponytail-review` when the installed
version supplies it separately; otherwise use verified integrated criteria.
If unavailable, use this fallback: trace the diff and connected callers for
correctness, safety, expected load, regression coverage, speed and unnecessary
complexity, in that order. No additional review agent or approval step.

Each finding names a concrete failing case, source location, smallest fix and
consequence. Fix in-scope acceptance failures and rerun affected checks. Keep
optional improvements separate; out-of-scope findings return to the coordinator
for deduplication in the existing backlog. A leaner diff is not review approval.
Retain exact candidate identity, required independent review and completion gates.

Offline handoff tests verify instruction delivery, not live worker adherence,
product acceptance or measured token/time savings.
